Дата: 2026-11-15. Статус: архитектура с первой реализацией альфы после дополнительного поручения владельца. Обязательные решения перечислены в [требованиях](../REQUIREMENTS.md); точный реализуемый контракт — в [alpha-contract.md](alpha-contract.md). Предложения полного поведения и фактические возможности альфы различаются ниже.

## Первая альфа

- `modules/NaSeqMen.Input.Windows` — самостоятельный DLL-модуль для обнаружения интерфейсов и Raw Input. Движение мыши по умолчанию не публикуется; оно включается через `includeMovement=true`. В соединении можно указать `captureLibrary` с абсолютным путём к DLL уже установленного Interception. Тогда Windows-интерфейсы, которые однозначно сопоставляются с драйвером, поддерживают временный захват.
- `modules/NaSeqMen.Desktop.Windows` — DLL-модуль действий клавиатуры через SendInput, запуска программы и условий активной/запущенной программы. Это механизм Windows, не перенос AHK.
- `modules/NaSeqMen.Obs` — DLL-модуль OBS WebSocket v5: авторизация, команды, ответы и события на одном подключении. При подключении нет автоматических Get-запросов или снимков. После разрыва требуется повторное подключение; автоматическое восстановление транспорта пока не реализовано.

Исполнитель загружает DLL при запуске из каталога `modules` рядом с EXE либо из `artifacts/alpha/modules` в рабочей копии. По умолчанию выполняется поиск `NaSeqMen.*.dll`. Файл `local/plugins.json`, если он есть, задаёт список имён DLL, например `["NaSeqMen.Input.Windows.dll", "NaSeqMen.Desktop.Windows.dll", "NaSeqMen.Obs.dll"]`. Модули используют общий контракт `INaModule`. Редактор получает каталог загруженных модулей по API и подбирает плагины под роль узла.
- `tests/NaSeqMen.ModuleChecks` — отдельная проверка через локальный mock WebSocket и подмену клавиатурного выхода, без SendInput. Дополнительный явно выбранный режим выполняет только GetVersion/GetSceneList/GetRecordStatus на экспериментальном OBS. Команды и границы проверки описаны в [README тестов](../tests/NaSeqMen.ModuleChecks/README.md).

Текущая альфа не заменяет `KOE.ahk`: чужой действующий перехватчик может поглотить или преобразовать физическую клавишу до того, как Raw Input её увидит. Работающий AHK не отключается. Режим изучения честно показывает только события, дошедшие до выбранного Windows-механизма.

### Имена операций и настроек альфы

| Модуль | Операции и параметры |
|---|---|
| `windows.input` | Соединение: `devicePath` (пусто — все наблюдаемые интерфейсы), `includeMovement` (по умолчанию false). Входы `key:1E`, `key:E0:1D`, `mouse:button1`…`mouse:button5`, `mouse:wheel`; фазы `down`, `up`, `change`. Номера мышиных кнопок здесь не являются нумерацией AHI. |
| `windows.desktop` | Действия `key(key,phase)`, `chord(keys)`, `launch(file,arguments)`; условия `foreground(process)`, `processRunning(process)`. Клавиша по имени либо `SC:1E`/`SC:E0:1D`; phase — down/up/press; сочетание — например Ctrl+C. |
| `obs` | Соединение: `url`, `password` либо `passwordEnvironment`. Действия `startRecord`, `stopRecord`, `toggleRecord`, `setMute(input,muted)`, `toggleMute(input)`, `setVolume(input,volume)`, `setScene(scene)`, `request(type,data)`. volume — число 0…1; data — JSON-объект. |

Сообщения OBS имеют Source `event` либо `response`, Control — имя события/запроса, Value — JSON поступивших данных. Это значение сообщения, не сохраняемое состояние. Разбор нужного поля доступен C# обработчику. Общее ядро не встраивает знание этих JSON-полей.

Отправка Windows ограничена механизмом SendInput и уровнем прав процесса; успешная передача ввода не доказывает выполнение команды выбранной программой. См. [официальное описание SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput). Собственный механизм наблюдения основан на [Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/using-raw-input); сторонние AHK-исходники в реализации не используются.

## Граница модуля

Модуль — самостоятельный подпроект и поставляемый пакет, который знает определённую систему или класс устройств. Он содержит описание доступных контактов и параметров, правила проверки конфигурации и реализацию обмена с внешней системой. Ядро знает общий контракт, но не команды OBS, HID-коды конкретной мыши или структуру экранов NaSDock.

Модуль может одновременно предоставлять источники событий/значений, проверки условий и действия. Делить интеграцию на два независимых подключения только из-за направлений обмена не нужно. Внутри модуля обработка ввода отделяется от отправки внешней команды: это позволяет исполнителю показать сформированное действие и подавить его отправку в пробном режиме.

Предлагаемый состав контракта, без фиксации классов и формата файлов:

| Часть | Что описывает |
|---|---|
| Идентификация пакета | Имя, версия модуля и поддерживаемая версия общего контракта |
| Настройка соединения | Поля подключения, проверка значений, пользовательское имя экземпляра |
| Контакты | Направление, тип полезной нагрузки, понятное название, описание |
| Действия | Параметры команды и граница, после которой происходит внешний эффект |
| Условия | Проверка внешней среды на момент обработки, результат проверки либо ошибка |
| Жизненный цикл | Подключение, отключение, отмена выполняемой операции, освобождение устройства |
| Диагностика | Поступление сообщения, прохождение этапа, сформированный выход, отказ или ошибка |

Набор реализованных возможностей объявляется явно. Нельзя показывать «подавить исходную клавишу», если выбранный механизм ввода умеет только наблюдать. Отсутствие возможности — свойство модуля, а не повод имитировать успешное действие.

## Один экземпляр соединения для обоих направлений

Пакет OBS устанавливается один раз. Пользователь может создать именованное соединение «OBS рабочий» и ссылаться на него из нескольких источников и действий схемы. Настройки и само подключение принадлежат этому экземпляру, а не каждой кнопке или линии схемы. Несколько подключений к разным экземплярам программы — разные именованные соединения того же модуля.

Входящее сообщение немедленно передаётся подключённым обработчикам. Исходящее действие адресуется выбранному соединению. Ответ внешней системы, если протокол его предусматривает, является отдельным поступившим сообщением, а не записью в общий каталог состояний.

При отключённом соединении действие получает ошибку доступности. Автоматически накапливать внешние команды и воспроизводить их после восстановления связи не предлагается. Переподключение восстанавливает транспорт и необходимые протокольные подписки, но не запрашивает начальный снимок и не рассылает запомненные значения.

Нет операции «выдать последнее значение», хранения наблюдаемого состояния, универсального начального согласования или обещания, что новый получатель немедленно узнает прошлое. Если пользователю нужен конкретный запрос к внешней программе, он явно собирает действие запроса и маршрут для поступившего ответа.

## Первые модули

| Рабочее имя | Назначение | Граница ответственности |
|---|---|---|
| Windows.Input | Устройства, интерфейсы, нажатие/отпускание, движение и колесо, распознавание и политика пропуска | Не знает, что боковая кнопка должна копировать или включать запись |
| Windows.Actions | Клавиатурный вывод: зажать, отпустить, нажать/отпустить, выполнить комбинацию | Получает сформированное действие; не выбирает его по физической кнопке |
| Windows.Context | Проверки активной программы и наличия процесса | Проверяет условие в момент вызова; не ведёт каталог состояний программ |
| NaSDock | Обмен с пультом: входные события и исходящие изменения элементов интерфейса | Не знает назначения OBS и конкретных Windows-комбинаций |
| OBS | Команды, ответы и события OBS WebSocket | Знает протокол OBS; не меняет элементы пульта непосредственно в обход схемы |

Это логические границы. Точное число сборок Windows-модулей и совместное использование низкоуровневого доступа к вводу следует определить при выборе реализации. Два модуля не должны конкурировать за владение одним перехватом устройства.

NaSDock остаётся отдельным проектом. Собственный протокол между ПК и пультом может не совпадать с протоколом интеграции на ПК. Например, модуль OBS принимает сообщение, схема преобразует значение, а модуль NaSDock отправляет команду пульту через его USB-транспорт. Пульт не обязан реализовывать OBS WebSocket.

Обратное сообщение внешней программы — обычный источник цепочки. Программное изменение отображения ползунка и физическое действие пользователя имеют разные виды сообщений. Установка отображаемого значения не должна сама порождать новое пользовательское событие и запускать бесконечное отражение через оба модуля.

## Составное устройство

Одно физическое устройство может предъявлять клавиатурный, мышиный и другие интерфейсы. Модуль обнаруживает доступные интерфейсы и показывает, откуда реально пришло событие. Совпадение модели/VID/PID не гарантирует, что это тот же экземпляр, если подключены два одинаковых устройства.

Предлагается сохранять селектор устройства и интерфейса, пользовательское имя и сопоставления. Временный системный номер устройства не должен становиться единственным постоянным ключом профиля. При неоднозначном совпадении профиль не применяется к случайному экземпляру; пользователь уточняет выбор. Подключение или переподключение устройства не должно менять профиль другого экземпляра.

Неизвестный интерфейс не объявляется поддержанным только потому, что обнаружен. Режим распознавания показывает наблюдаемые данные; поддержка специальных vendor-протоколов является задачей конкретного модуля.

## Режим распознавания и настройки

Режим обслуживается модулем ввода в исполнителе, а отображается редактором. Это часть настройки устройства, не отдельный движок и не второй независимый перехватчик.

1. Выбрать физическое устройство и доступные интерфейсы.
2. Выбрать наблюдение с пропуском либо перехват с подавлением в явно заданной области.
3. Нажимать физические кнопки, просматривая поток событий с интерфейсом, кодом, фазой нажатия/отпускания, значением и порядком поступления.
4. Дать найденному контакту понятное имя и выбрать сопоставление. Если одна кнопка выдаёт несколько событий, сначала показать последовательность; не сливать её автоматически в выдуманное единичное нажатие.
5. Задать судьбу исходного ввода и событие, передаваемое в схему.
6. Сохранить профиль конфигурации. Увиденные нажатия не становятся сохранённым состоянием источника.

Точные элементы таблицы, фильтрация и редактирование описываются в [архитектуре редактора](editor.md). Название кнопки в обычной схеме — пользовательское; технические коды доступны в режиме распознавания и подробностях.

## Политика физического ввода

При открытии активной вкладки «Устройства и события» редактор включает обнаружение для настроенных составных мышей. Другие интерфейсы выбираются в строках таблицы. Обнаруженные сигналы выводятся в редактор и пропускают маршрутизацию схемы. Если драйвер подтвердил установку фильтра, клавиши, дополнительные кнопки мыши и колесо подавляются также в Windows. Движение указателя и основное нажатие остаются доступны для работы с редактором. Смена вкладки, потеря фокуса или прекращение продления сеанса возвращают обычный ввод.

Политика имеет область: экземпляр устройства, интерфейс и вид ввода. Это важно для мыши с вредными дополнительными клавишами: блокирование всех неназначенных клавиш не должно автоматически отключать перемещение указателя.

| Политика | Исходный ввод в Windows | Сообщение в схему |
|---|---|---|
| Наблюдать | Проходит | Поступает для наблюдения/обработки |
| Блокировать | Подавляется | Может быть виден диагностике, действие не назначено |
| Переназначить | Подавляется | Выдаётся именованное событие для подключённого правила |
| Пропустить без назначения | Проходит | Не требуется отдельное назначенное событие |

Для неназначенных событий задаётся отдельная политика по умолчанию. Для проблемного устройства допустима «блокировать»; для другой клавиатуры она не применяется автоматически. Если условие в схеме не прошло, исходный ввод не возникает заново: пропуск оригинала — отдельное решение входного модуля, а не скрытый эффект фильтра.

Нажатие и отпускание передаются как отдельные события. Выходные действия также различают зажатие, отпускание и короткое нажатие. Переподключение, отмена или смена конфигурации не должны оставлять сгенерированный модификатор зажатым. Механика завершения активного ввода относится к выполняемой операции, не предоставляет пользователю хранилище значений.

В альфе Desktop отслеживает только владение собственными активными нажатиями по соединению и источнику. Повторный down не требует дополнительных up. Общий модификатор отпускается после завершения последнего собственного владельца. Клавиша, уже удерживаемая перед действием, не присваивается модулем и не отпускается его cleanup. Ошибка отпускания не теряет сведения об операции: её можно повторить; остальные клавиши всё равно обрабатываются. Полное различение одновременно меняющегося физического и синтетического ввода требует отдельной аппаратной проверки и не заявлено результатом mock-тестов.

## Отладка ввода и граница внешних эффектов

В пробном прогоне видно исходное событие, выбранное сопоставление, решение условия и сформированное выходное действие. Исполнитель не отправляет это действие наружу. Успешное формирование не изображается как успешное выполнение внешней программой.

Судьба исходного физического нажатия задаётся отдельно: подавить сгенерированное сочетание недостаточно, чтобы исходная кнопка перестала воздействовать на Windows. Редактор должен одновременно показывать режим пробного выполнения и область перехвата. Выход из захвата остаётся доступным через не перехваченное устройство или обычное управление редактором.

Поток диагностики идёт от исполнителя к редактору, а не через редактор обратно в рабочую цепочку. Задержка, закрытие или потеря связи с редактором не должны тормозить физический ввод. Поведение при завершении режима настройки следует определить явно; нельзя оставлять случайно активный захват после закрытия окна.

## Выбор механизма Windows-ввода

Выбор ещё не сделан. Требуется отдельно проверить обнаружение конкретного устройства, различение одинаковых экземпляров, наблюдение клавиатуры/мыши и подавление ввода выбранного устройства. Возможность наблюдать не доказывает возможность перехватывать.

Raw Input используется для наблюдения. Временный захват в редакторе использует опциональное подключение внешней DLL Interception через публичный ABI. Проект не включает драйвер или DLL, не устанавливает их и не использует исходники AutoHotkey или AutoHotInterception.

Ни AutoHotkey, ни AutoHotInterception не являются основой собственной реализации. Исходники не копируются, не переводятся и не адаптируются. Локальный сценарий владельца используется только для описания входов и ожидаемых выходов в [локальной поведенческой заметке](../local/koe-behavior.md); заметка исключена из публикации правилом local/.

## Проверки будущей реализации

- Два одинаковых устройства: назначение применяется только к выбранному экземпляру.
- Составная мышь: клавиатурные кнопки и мышиные кнопки различимы; движение не теряется из-за политики для клавиш.
- Неназначенные клавиши выбранного интерфейса блокируются, обычная отдельная клавиатура продолжает работать.
- Нажатие/отпускание и последовательности совпадают с описанным поведением, включая порядок модификаторов.
- Отмена и смена конфигурации завершают сгенерированные удержания, не выполняя новый макрос.
- Пробный прогон показывает выход без отправки; политика исходного физического ввода проверяется отдельно.
- Закрытие редактора не останавливает рабочие правила; завершение захвата настройки имеет предсказуемое поведение.
- Модуль OBS заменяем другим модулем без изменения ядра; одна связь используется источниками и действиями.
- После подключения нового получателя или восстановления транспорта нет рассылки сохранённых значений и отложенных команд.

Этот полный набор проверок описывает целевое поведение; он не объявлен пройденным альфой. В частности, подавление физического ввода и модуль NaSDock пока не реализованы. Рабочий AHK и настройки реальных устройств не изменяются при проверках альфы.
